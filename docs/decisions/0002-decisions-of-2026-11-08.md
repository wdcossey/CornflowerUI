# ADR 0002 — Decisions of 2026-11-08

**Date:** 2026-11-08 · **Status:** Accepted

## Context

The repo was bootstrapped on 2026-11-08: the solution, the build gate, CI and auto-discovery, with
no controls. Before that, the project was planned in working notes outside the repo. The open
questions in those notes were put to the maintainer, who ruled on all of them on 2026-11-08,
alongside [ADR 0001](0001-what-faithful-means.md). This records the decisions later work
inherits, each with its reason. One of them, the shape of a control, was accepted the day before
and is recorded here so that it has a home in the repo.

## Decision

### Reference material

| Question | Decision | Why |
|---|---|---|
| May Microsoft's SDK files be used? | Microsoft's Windows Phone 8.1 SDK templates (`generic.xaml`), theme resources (`themeresources.xaml`) and API metadata (`Windows.winmd`) are **read as a specification**. They are kept outside the repo, and every template is written new. A qualified legal opinion is obtained **before the first NuGet release**. This is not legal advice | The files are under Microsoft's proprietary SDK terms. They fix geometry, states and resources exactly, which captures alone would lose. A WinRT template can't be reused in Avalonia anyway. The repo is public, and holds no Microsoft content |
| Do emulator captures go in the repo? | The **PNGs are committed**, under `ref/wp81/<control>/`. The **JSON template-tree dumps stay outside the repo**; a plan quotes the numbers it uses and names the dump they came from | A reviewer needs the screenshot beside ours. The dumps hold values read out of Microsoft's templates as the phone resolved them (sizes, brushes, state setters), which is closer to the templates themselves than a picture is. A plan needs only a few of those numbers |
| Where do the reference app and the spec tools live? | In the repo's `tools/`: the reference app and its capture script (`tools/refapp`), the `.winmd` reader (`tools/winrt-api`) and the font measurement scripts. The reference app's placeholder logos are already our own, written when it was made | A capture tool should be versioned with the captures it makes |

The capture decision may be revisited: the maintainer asked whether keeping the JSON dumps in
the repo does any harm. Until that is answered, they stay out.

### Themes and scope

| Question | Decision | Why |
|---|---|---|
| What renders a control we haven't themed yet? | During development, Avalonia's **Simple theme sits underneath** `Wp81Theme` in the sample and the tests. A test lists every templated Avalonia control without a Wp81 theme; **its count is the measure of completeness**. `Wp81Theme` doesn't include a fallback: a shipped app chooses its own | A `ControlTheme` replaces the previous one whole, so an unthemed control gets no template at all, or Fluent's if that is installed too. Putting Simple inside `Wp81Theme` would add a dependency and a mismatched look to every app. What a control with no theme does is confirmed by a Tier 0 spike |
| Controls Avalonia has and the phone never did (TreeView, DataGrid, Calendar, SplitView, Menu, TabControl, Expander, NumericUpDown, ColorPicker and others) | A plain theme in the era's style for each, labelled as ours and not a reproduction, in a late tier | Without one, an app using the control gets no template. There is nothing on the phone to reproduce |
| Windows Phone 8.0's Silverlight-only controls (Panorama, LongListSelector, HubTile, the toolkit's ListPicker) | After era 1, as an add-on to it | They exist only in the Silverlight stack, need the 8.0 emulator, and have no published source. Era 1 goes to depth first ([ADR 0001](0001-what-faithful-means.md#consequences)) |

### Fonts and colour

| Question | Decision | Why |
|---|---|---|
| Selawik Semilight reports `usWeightClass` 300, the same as Light | Address the Semilight file by its own family name. Patch the font only if that fails | Asking for `FontWeight="SemiLight"` may pick the Light file. Patching means shipping a renamed derivative under the OFL. A headless test settles whether addressing by name works |
| Fallback for scripts Selawik lacks | **Noto Sans, in a separate optional package, `Cornflower.Fonts.Noto`** | Selawik has 348 code points, Latin-1 and Latin Extended-A, with no Greek or Cyrillic. Bundling Noto Sans in the theme package would add several MB to every app; this way a Latin-only app stays small. Text in other scripts will be about 6% wider than the reference |
| Default accent colour | **`#3E65FF`**: the emulator's default `PhoneAccentBrush` (`#FF3E65FF` in both themes), as the reference app read it on 2026-11-08. The 20 named accents become resources an app can pick from | It is measured: it is what an untouched Windows Phone 8.1 emulator shows. The 20 names are the same in the 8.0 and 8.1 SDK design files; their values are still to be compared file by file |

The accent was read on the 720p profile, and read again on the reference profile (device 11)
and on device 12 on 2026-11-08: `#FF3E65FF` on all three.

### The shape of a control

Accepted 2026-11-07. The question was whether Cornflower should be its own set of control
classes, as Avonic is, or a theme over Avalonia's controls.

**Decision: a hybrid, with a ladder.** For each difference between Avalonia's control and the
phone's, found in a control's Compare step, take the first rung that reaches the measured
behaviour, and record the rung in the control's plan:

1. Theme.
2. Attached behaviour.
3. Part class: our own control inside Avalonia's template.
4. Subclass keeping the WinRT name, under stated conditions.
5. New control with the WinRT name.
6. Recorded deviation.

The rungs and the conditions on a subclass are set out in
[the architecture](../ARCHITECTURE.md#the-limit-of-a-theme).

**Why.** Avonic is all its own classes because Ionic's API has no Avalonia shape. The phone's
XAML control set does: Avalonia's classes already raise the states most phone templates use. A
pure theme can't reach ComboBox's full-screen mode, list check mode and reorder, or scroll
physics. A full set of our own classes would rebuild what Avalonia already does right (text
editing, selection, virtualisation, automation, keyboard), and every app would change every type.
The ladder keeps Avalonia's types for most controls, and costs an app a type change only for the
listed subclasses and the new controls.

Expected from reading the 8.1 templates against Avalonia 12.1.4: one subclass (ComboBox, for its
full-screen mode), one likely part class (scroll physics), and eight families of new controls.
That is a plan, not a result.

## Consequences

- Nothing Microsoft wrote enters the repo: no template, no resource file, no font, no `.winmd`,
  and no logo from a Visual Studio template. A CI check for this is a Tier 0 item.
- A plan that uses a number from a JSON dump quotes it and names the dump, since a reviewer can't
  open the dump from the repo.
- The holes test's count is how the roadmap measures era 1's completeness.
- A control that climbs a rung of the ladder says so in its PR. A subclass is listed as a type
  substitution in its control's README.
- The two Tier 0 spikes the ladder needs (a subclass theme `BasedOn` the base's; a tilt behaviour
  reading the press point on a stock `Button`) run before Tier 1.
